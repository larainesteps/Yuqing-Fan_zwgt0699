# Appendix B Ethical Issues Addressed

This appendix records the ethical review status of the project and the specific measures
implemented in support of the position set out in Section 1.4. Section 1.4 states the
position and the reasoning behind it; this appendix documents what was done.

## B.1 Ethical review status

No ethical review application was required for this project. It uses no identifiable
patient records, recruits no human participants, and collects no personal data. Development
and evaluation used synthetic case text, the publicly available PMC-Patients dataset
(Zhao et al., 2023), and the synthetic appointment dataset of Gonzalez Galtier (2024), whose
publisher states that it was synthetically generated and may not reflect real-world data. No
data was obtained from a healthcare organisation.

## B.2 Data protection

Health information is special category data under the UK GDPR (Information Commissioner's
Office, 2024), and its processing requires both a lawful basis and a special category
condition (Information Commissioner's Office, n.d.). Appointment data can reveal health
information where it identifies the type or context of care.

Measures taken:

- No identifiable patient records were used. Patient and staff identifiers in the prototype
  are artificial or dataset identifiers.
- The intake interface displays a de-identification instruction before any note is
  submitted (Figure 4.5), and the contract requires a `deidentified` flag on every note.
- Database credentials and the API key are held in local environment configuration and are
  excluded from version control by `.gitignore`. The key-configuration script collects the
  key as a `SecureString`, writes it to the user environment, and never echoes or stores it
  in the project.

A hospital deployment would additionally require a documented purpose, data minimisation,
retention rules, access controls, a processing risk assessment, and — for the language model
path — an approved data-processing arrangement with the provider.

## B.3 Human oversight and clinical safety

The central safeguard is that **no extraction can reach a schedule without a human
decision**, and it is enforced structurally rather than by a check that could be bypassed:
the API provides no route that creates an approved case (Sections 3.2.4 and 4.5). Every
extraction — from the language model and from the rule engine alike — enters
`REVIEW_REQUIRED` and stays there until a reviewer approves or rejects it.

Supporting measures:

- The original note is retained beside the structured record, so a reviewer compares the
  extraction against its source rather than approving a record they cannot check.
- Validation warnings and the extraction path are stored with each record.
- The priority score is a planning aid, not a triage decision. Its components are exposed so
  that it can be questioned (Sections 2.1.2 and 4.4).
- Clinical deadlines are hard constraints. A case that cannot meet its deadline is returned
  unscheduled with a reason, never scheduled late. Section 5.3 documents the defect in which
  this was not true and how it was corrected.

## B.4 Bias, fairness and explainability

Historical appointment data can encode the effects of earlier capacity shortages or unequal
access, and optimising against those records without review could reproduce them. The
project limits this by using explicit scheduling fields, deterministic validation, visible
warnings and manual approval. Protected characteristics are not optimisation rewards.

Doctor workload is reported through the Jain fairness index, with its limitations stated:
equal case counts are not necessarily equitable once complexity, seniority, training and
contracted hours are considered. The index compares schedules; it does not certify an
allocation as fair (Section 2.2.4).

## B.5 Accountability and auditability

Case review decisions, optimisation requests and results, rejected cases, locked
allocations, emergency changes and resource bookings are all persisted. `case_audit_events`
records a before-and-after document for every transition, and `optimization_runs` stores the
request that produced each result, so any output can be traced to the input and
configuration that generated it. This supports investigation; it does not transfer
responsibility from the user to the software.

## B.6 Scope and limits of use

The prototype is research software. It is **not** a medical device and not a validated
clinical system, and this report makes no claim of clinical effectiveness or deployment
readiness (Section 6.1.4). Any proposed operational use would require separate legal and
regulatory assessment, clinical risk management, security testing, organisational approval
and evaluation with representative data — all outside the scope of an MSc project.

## B.7 Social and operational considerations

Automated scheduling can reduce repetitive work but can also encourage overreliance on a
score or a solver result. The interface therefore reports rejection reasons, conflicts,
hard-constraint violations and the changes made during emergency rescheduling, and manual
locks preserve decisions that should not move automatically.

Resource utilisation is not treated as the sole measure of a good schedule. Pushing
